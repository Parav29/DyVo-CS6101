## Differences from the paper

| # | Difference | Effect |
|---|---|---|
| 1 | GPU: 1 × RTX A5000 24 GB on a shared machine (paper: 1 × A100) | Speed only |
| 2 | **Course budget:** batch 4 × 4 gradient accumulation = effective batch 16 (the YAMLs would inherit 128) | Same objective: KL and L1 are batch means and each query only sees its own pos/neg pair (no in-batch negatives); only fp16 rounding differs |
| 2a | `*_course20k` rows only: 20k optimizer steps instead of 100k; LR warm-up (10%) and linear decay scale with it | Less training: absolute numbers are expected below the paper's |
| 2b | L1 warm-up `T`: the regularizer steps once per micro-batch, so T = 50k × 4 = 200000 (100k runs) and 10k × 4 = 40000 (20k runs) reach full weight at half of training, as in the paper (50k of 100k) | Same regularization schedule as the paper |
| 2e | GPT4 / Mixtral rows reuse the DyVo (REL)-trained model and change only the test query candidates, as the paper states (Table 3 caption: "Entity candidates generated by GPT4 are used on queries for inference"). Candidates are the authors' LLM outputs (`queries_entities_{gpt4,mistral}.jsonl`); no LLM was called | Faithful; the paper trains one model per row, which with identical data and seed should be equivalent up to GPU non-determinism |
| 2c | **Course budget:** no mid-training evaluation (every 5k steps on 100k docs in the official config) | None: it only logs; no best-checkpoint selection |
| 2d | Extra reference rows: the authors' init checkpoint evaluated without training (`*_init`: 1 step with learning rate 0) | Not in the paper |
| 3 | λ_ent sits inside the ReLU in the code (`log1p(relu(λ·e·h))`), outside in Eq. 4 | Official code kept |
| 4 | `loss.normalize: "std"` is actually L2 normalization of MonoT5 scores | Official code kept; scores checked non-negative |
